## 1. Entry Points

| Entry Point | Trigger | File:Line |
|---|---|---|
| **Node.js process** | `npm start` / `npm run dev` | `src/index.ts:364` (`main()`) |
| **WhatsApp messages** | Incoming WA messages via Baileys | `src/whatsapp/client.ts:287` (messages.upsert) → `src/whatsapp/dispatch.ts:69` (handler) |
| **HTTP API** | GET requests to `127.0.0.1:3000` | `src/api/server.ts:79` (http.createServer) |
| **Cron scheduler** | node-cron scheduled tasks | `src/scheduler/scheduler.ts:213,238,274` (cron.schedule) |
| **CLI scripts** | `npm run fetch`, `npm run db:reset`, etc. | `package.json:24` (inline ts-node/node scripts) |

### How entry points connect

1. `src/index.ts:84` — `main()` orchestrates all startup: loads config, inits DB, fetches data, starts API server, creates scheduler, connects WhatsApp.
2. WhatsApp client (`src/whatsapp/client.ts:287`) fires `messages.upsert` events → registered handlers at `src/whatsapp/dispatch.ts:69` parse commands → route to report generators or admin handlers.
3. HTTP API (`src/api/server.ts:102`) routes GET requests to report data handlers, which call `computeMembers()` directly.
4. Cron scheduler (`src/scheduler/scheduler.ts:198`) fires callbacks at configured times → delegates to `ReportOrchestrator.sendReport()` via callbacks.

### Circular dependency check

**No circular dependencies found.** The codebase uses two patterns to avoid cycles:

1. **Type-only imports** — `report-orchestrator.ts:10-11` imports `UmaMoeClient` and `WhatsAppClient` as `import type`, not value imports. This creates a compile-time-only reference.
2. **Extracted ensure-snapshot** — `data/ensure-snapshot.ts:14` imports `UmaMoeClient` as a type. The function is re-exported through `data/snapshot.ts:248` to preserve the public API while avoiding a data→api dependency (`docs/architecture.md:116`).
3. **Callback injection** — `scheduler/scheduler.ts:20-21` receives `onReport` and `onCombinedReport` as callbacks rather than importing the orchestrator directly.

## 3. Data Flow

### Inbound: Data Acquisition

```
uma.moe API → UmaMoeClient.fetchCircleData() → Snapshot (JSON) → data/snapshots/YYYY/MM/DD.json
```

1. `src/api/uma-moe.ts:73` — `fetchCircleData()` opens Playwright browser, solves Cloudflare Turnstile, fetches `/api/v4/circles` endpoint.
2. `src/api/uma-moe.ts:82-122` — Retries up to 3 times on 401/403 (token refresh).
3. `src/data/snapshot.ts:50` — `saveSnapshot()` writes atomically (tmp + rename) to `data/snapshots/YYYY/MM/DD.json`.
4. `src/data/ensure-snapshot.ts:24` — `ensureMonthSnapshot()` checks disk cache first, fetches on miss. Called at startup and before monthly reports.

**When data is fetched:**
- On startup (`src/index.ts:218-233`) — if snapshot is 2+ days stale
- On scheduled data fetch (`src/scheduler/scheduler.ts:156-167`) — same cron as daily report
- On-demand via `npm run fetch` (`package.json:24`)
- On report request with month mismatch (`src/orchestrator/report-orchestrator.ts:101-140`)

### Outbound: Report Delivery

```
Snapshot → computeMembers() → ReportOrchestrator.sendReport() → generateReport() → deliverReport() → WhatsApp
```

1. `src/reports/compute.ts:35` — `computeMembers()` transforms `daily_fans` arrays into `ComputedMember[]` with gains, status, weekly breakdowns. Called once per pipeline.
2. `src/orchestrator/report-orchestrator.ts:265-307` — `sendReport()`: aligns snapshot to month, pre-fetches target month, generates report string, delivers via WhatsApp, processes alerts.
3. `src/reports/registry.ts:25` — `generateReportString()` routes to the correct generator (daily, weekly, monthly, etc.).
4. `src/orchestrator/report-orchestrator.ts:48-70` — `deliverReport()` sends to all announcement groups via WhatsApp.
5. `src/whatsapp/client.ts:444` — `sendMessage()` auto-splits at newline boundaries.

### Alerts

```
Snapshot → detectAlerts() → recordAlert() → formatAlerts() → WhatsApp → Admin/Group
```

1. `src/alerts/alerts.ts:35` — `detectAlerts()` checks: performance drop, demotion risk, streak break, new transfer, rank drop.
2. `src/alerts/alerts.ts:156-160` — Deduplication via batch `getExistingAlertKeys()`.
3. `src/alerts/alerts.ts:162-199` — Quiet hours suppress but still record for dedup.
4. `src/orchestrator/report-orchestrator.ts:184-225` — `processAlertsForReport()` records alerts, delivers, and marks sent.

### Catch-up flow

```
Startup → CatchUpManager.detectMissedReports() → executeCatchUp() → sendReport() (tagged ⚠️ Catch-up)
```

1. `src/scheduler/catchup.ts:55` — `detectMissedReports()` compares last DB run against most recent scheduled day per report type.
2. `src/scheduler/catchup.ts:179` — `executeCatchUp()` groups colliding reports, sends oldest-first, respects `maxReportsPerStartup`.
3. `src/orchestrator/report-orchestrator.ts:159-163` — Catch-up tag `*⚠️ Catch-up*` inserted below report title.

## 8. Documented Design Decisions

The following design choices are explicitly documented in `docs/architecture.md:422-451` as accepted. These should NOT be flagged as issues in reviews.

### 8.1 Rate limiter Map is unbounded (`api/server.ts:55`)
The `requestTimestamps` Map is never pruned. Accepted because the API binds exclusively to `127.0.0.1` — at most 2 loopback entries.

### 8.2 WA_SESSION_DIR is not path-sanitized (`whatsapp/client.ts:139`)
The env var is used directly as a filesystem path. Accepted because the bot operator controls it — an attacker with env access already has process-level access.

### 8.3 Security headers are minimal (`api/server.ts:32-34`)
HSTS and X-XSS-Protection omitted. Accepted because the API serves only JSON, binds to localhost, has no browser-rendered content.

### 8.4 Runtime stats use module-level mutable state (`runtime.ts:21-39`)
Singleton pattern with shallow-copy getter. Accepted as standard Node.js pattern for single-process apps.

### 8.5 Logger uses synchronous file I/O (`utils/logger.ts:183,189`)
`appendFileSync` on every log line. Accepted at current scale (~100 log lines per report cycle).

### 8.6 Catch-up persistence has a narrow window (`scheduler/catchup.ts:217-233`)
~10ms window between saving combined run and individual records. Accepted because real-world crash risk is negligible.

### 8.7 computeRollingAverage excludes zero-gain days (`data/daily-fans.ts:249`)
`gain > 0` filter computes "average when active" not "average over time". Explicitly documented — downstream thresholds should account for this.

### 8.8 Ghost detection edge case (`reports/compute.ts:90-104`)
Transfer members with low gain could theoretically be misclassified as "left". Accepted — requires `ghostCount > (zero-gain + stale members)`, which doesn't occur with real data (34 members, ghostCount=4).

### 8.9 WhatsApp client is a large file (`whatsapp/client.ts`, 608 lines)
Connection lifecycle concerns are inherently coupled to Baileys' state machine. Splitting would increase cross-module coupling without reducing complexity.

### 8.10 Single-process architecture (`docs/architecture.md:1-5`)
Data processing is arithmetic on arrays of ~34 integers. uma.moe data is static for 24h. Splitting into microservices adds operational friction without benefit.

### 8.11 Immutable snapshots (`docs/architecture.md:49`)
Reports are pure functions on the `daily_fans` array. Recomputing from the same data always produces the same result. Mutating saved data would break this invariant.

### 8.12 sql.js not sqlite3 (`CONTRIBUTING.md:251`)
Uses in-memory WASM SQLite. No native compilation needed. DB file is a binary blob.

### 8.13 Config hot-reload via polling (`docs/architecture.md:173`)
Polls mtime + content hash every 5s. Schedule changes trigger scheduler restart automatically.

### 8.14 Collision handling (`docs/configuration.md:183`)
When daily + weekly are scheduled at the same time on the same day, only the daily handler fires. It detects the collision and sends a combined message.

### 8.15 Baileys doesn't clean up (`CONTRIBUTING.md:252`)
Tests use `--forceExit --detectOpenHandles` because Baileys sockets don't close cleanly.

### Why this order (from `docs/architecture.md:97-102`):
- Config must load first (everything depends on it)
- Data must be available before reports can generate
- API server starts before WhatsApp (independent)
- Scheduler starts before WhatsApp (handles WA-not-connected gracefully)
- WhatsApp connects last (needs QR scan on first run)
- Catch-up runs after WhatsApp connects (needs to send messages)

## 10. Observations

These are factual observations about code patterns — not risk signals, since each has been documented as an accepted design choice:

1. **pino is a listed dependency but not directly imported** in any `src/` file. It may be used internally by Baileys or as a transitive dependency. (`package.json:42`)

2. **`src/utils/index.ts` does not exist** despite being listed in `AGENTS.md:76`. The utils module has three separate files (format, logger, timezone) with no barrel export.

3. **The `settings` table** is documented in `docs/architecture.md:143` as "future use, no IDatabase methods yet" — the table exists in both SQLite and MySQL adapters but has no read/write methods in IDatabase.

4. **Test structure is extensive** — the `tests/` directory mirrors `src/` with unit, format, dispatch, stale, edge, regression, integration, and golden-file test categories. Coverage thresholds are 70% branches, 80% functions/lines/statements.

5. **playwright is a runtime dependency** (`package.json:42`) that requires browser installation. Docker builds include Playwright chromium and system deps (`AGENTS.md:198`).
